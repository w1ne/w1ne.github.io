The industrial automation world is standardizing on IO-Link (IEC 61131-9). Yet, for embedded firmware engineers, integrating IO-Link into a custom sensor often means fighting against vendor-locked binary blobs or deciphering spaghetti code that mixes protocol logic with SPI driver calls.

I built **iolinki** to prove that an industrial fieldbus stack can be modern, testable, and completely decoupled from hardware.

> **Source Code**: [github.com/w1ne/iolinki](https://github.com/w1ne/iolinki)

# Key Architecture Decisions

## 1. Radical Hardware Independence

Most embedded stacks claim to be "portable" but are riddled with `#ifdef STM32` or implicit assumptions about the timer peripheral. `iolinki` takes a different approach: **Pure Abstraction**.

The stack interacts with the hardware *solely* through a `iolink_phy_api_t` structure of function pointers.

```c
typedef struct {
    int (*init)(void);
    int (*set_mode)(iolink_mode_t mode);
    int (*send_byte)(uint8_t byte);
    int (*read_byte)(uint8_t *byte);
    // ...
} iolink_phy_api_t;
```

This strict boundary means the protocol logic (`dll.c`) literally cannot access hardware registers. This architectural constraint forces cleaner code and enables the "Killer Feature": **Simulation**.

## 2. Test-Driven Development (TDD) via Virtual PHY

Because the PHY is an interface, we can mock it.
`iolinki` was developed using a **Virtual PHY** that pipes data to a Python-based IO-Link Master simulation (`tools/virtual_master`).

This allows us to run **36 automated conformance tests** in a CI/CD pipeline (GitHub Actions) without a single piece of real hardware connected.

### Conformance Coverage
We validate against IO-Link V1.1.5 specification requirements:
*   ✅ **State Machine**: All transitions (Startup → Preoperate → Operate) validated.
*   ✅ **Timing**: Cycle times and wake-up pulses measured to microsecond precision in simulation.
*   ✅ **ISDU**: Full coverage of all 12 mandatory indices (0x0010 Vendor Name, etc.).
*   ✅ **Error Injection**: We inject CRC errors and timeouts to verify the stack's recovery logic.

## 3. Zero-Malloc Safety

In industrial controls, heap fragmentation is a bug waiting to happen. `iolinki` uses a **static memory model**.
*   **No `malloc`/`free`**: All buffers are allocated at compile time.
*   **Deterministic Execution**: The `iolink_process()` loop is designed to have a bounded execution time, making it safe for real-time control loops.

## 4. Zephyr RTOS Integration

While the core is bare-metal compatible, `iolinki` shines on Zephyr. It integrates as a native module:
*   **Logging**: Uses Zephyr's logging subsystem for transparent debugging.
*   **Shell**: Exposes stack status and statistics via the Zephyr console.

# Technical Deep Dive: The Data Link Layer

The heart of the stack is the Data Link Layer (DLL) state machine. It handles the critical "M-Sequence" exchange.

1.  **STARTUP**: The stack waits for the Wake-Up pulse (WURQ).
2.  **PREOPERATE**: The Master requests parameters (MinCycleTime, FrameCapability) at 230.4 kbaud (COM3) or lower.
3.  **OPERATE**: The stack enters the cyclic Process Data (PD) exchange.

This transition logic is notoriously tricky due to strict timing requirements (e.g., specific response windows). By unit-testing the state machine with `cmocka`, we ensure that edge cases—like a Master dropping out mid-handshake—are handled correctly every time.

# Conclusion

`iolinki` is an attempt to bring modern software engineering standards—CI/CD, TDD, and modular architecture—to the somewhat archaic world of industrial fieldbus firmware. It provides a robust, verified foundation for building the next generation of smart sensors.
